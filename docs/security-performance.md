# Security, compression and CDN upgrade — 26 November 2026

This is a code and additive migration update. It does not apply changes to the remote Supabase project or enable a paid service. Existing migrations and historical business records are preserved.

## Apply to an existing project

1. Run **only** `supabase/migrations/202611260001_security_and_images.sql` once in the trusted SQL Editor. The original three migrations must already be applied. New projects apply all four in order. The new migration is required for sign-in throttling, catalogue paging and new image uploads; deploy it before using the updated application.
2. Generate a fresh Supabase server secret. Add `SUPABASE_SECRET_KEY` to the existing ignored `.env.local` and to the deployment's **server** environment. Preserve the existing public project URL and publishable key. Do not share the secret in chat or prefix it with `NEXT_PUBLIC_`. The previously shared secret/password should be replaced through trusted Supabase administration; no remote credential changes were performed here.
3. Restart `npm.cmd run dev`, or run `npm.cmd run build` and deploy/restart production with the new configuration. Missing Storage credentials produce a clear upload setup error. Login, orders and ordinary catalogue reads do not require the server secret.
4. As office/admin, upload a product image and inspect the private `catalogue` bucket. Expect content-addressed WebP objects and an attached image manifest. As an approved customer, view the product and inspect responsive image requests. As an anonymous/unapproved/delivery user, verify catalogue access is denied. Attempt a direct Storage upload with a staff JWT: it must be denied. Do not make the bucket public.

## Image processing and delivery

- The browser lazily loads a preprocessing module only on upload. Where supported it reduces large photos to a 1600-pixel longest edge and uploads a smaller WebP when that saves bytes. The browser's result is never trusted as validation.
- The server checks role/approval first, validates the product and file limits, consumes a persistent hourly upload quota, checks raster signatures, and decodes with Sharp. Supported input is JPEG/PNG/WebP, up to 8 MB and 20 megapixels. SVG, unknown formats, truncated/forged files and oversized pixel dimensions are rejected. Animated formats reported by the decoder are rejected; no uploaded original is served unchanged.
- EXIF/GPS/camera metadata and original color-profile metadata are removed. Orientation is applied to pixels. Output remains transparent when the source is transparent. Up to three WebP variants fit within 480, 960 and 1600-pixel boxes at quality 80; small inputs are not enlarged. Individual outputs are capped at 2 MB. Two server encoding jobs may run concurrently per application worker; extra jobs receive a retry message.
- Only the server-only Storage writer can write/delete bucket objects. Ordinary staff JWTs have no Storage insert/delete policy, so they cannot bypass decoding with direct uploads. The writer is constructed only inside the already-authorized server action, uses a separate Supabase client without cookies/sessions, and exposes only the catalogue bucket API. The original user's JWT attaches the manifest through a constrained RPC, preserving audit attribution.
- Objects use `product-id/SHA256-input/actual-width.webp`. Uploads never overwrite an object. Byte-identical uploads of a product are deduplicated; simultaneous attachment retries return the existing image record. Old JPEG/PNG objects remain readable through the legacy signed-image fallback; they are not retroactively stripped/compressed. Re-upload a legacy photograph to create optimized versions. The latest uploaded photograph is shown first.
- Catalogue lists render responsive `srcset`, lazy loading and asynchronous decoding; the main product-detail photo is eager. Signing is batched for all visible variants. A bounded, actor/project-partitioned in-process cache reuses image URLs for at most 255 seconds. Each cache lookup occurs **after** request authorization; user profiles, session tokens, prices and customer records are never stored in this cache. Multiple workers have independent expendable caches.
- Photos are served directly by Supabase Storage rather than proxied through the application server or the public Next Image cache. They remain in a private bucket and use 300-second signed URLs and 300-second object response cache duration. No extra image-transformation subscription is required because the app prepares the variants itself. Supabase's **Smart CDN** behavior depends on the project plan and is enabled automatically on Pro and above; no plan change was performed. [Supabase Smart CDN documentation](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

Signed links are bearer capabilities. A previously issued link and its cached response can remain usable after a role change or sign-out; token expiry and response-cache lifetime are separate, and the effective window may include both durations. There is no claim of immediate revocation for downloaded photos. Emergency removal requires trusted object deletion/CDN invalidation, which Supabase documents can take up to a minute to propagate. This trade-off applies to catalogue photos, never trade-price pages or customer financial records. [Supabase signed URL/cache behavior](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

Files successfully uploaded before a later Storage/DB failure may remain unreferenced. The action deliberately avoids deleting shared content-addressed paths during a failed retry, which could remove another simultaneous request's successful image. Trusted maintenance may remove **old unreferenced objects** after checking all image paths/variant manifests; do not delete Storage metadata rows directly or run a blind bucket wipe.

## Security fixes

- Public configuration rejects modern secret keys, legacy service-role JWTs, credential-bearing URLs, non-root API URLs and non-local plaintext HTTP. Only publishable keys or legacy anon JWTs are accepted for browser configuration. The Storage secret module is explicitly server-only.
- A database-backed sign-in budget allows 10 attempts per normalized email and 200 globally per minute. Email identifiers are hashed in a private RLS-protected table, counters saturate, and globally rejected requests do not allocate new per-email rows. Failed quota infrastructure fails closed. This complements Supabase Auth controls; it does not replace the provider's direct-API rate limits, bot protections or an edge firewall. No untrusted forwarded IP header is used as an identity. Uploads are limited to 30 attempts/hour per authorized actor. The server-only credential and direct-write policy denial prevent staff from bypassing that application upload path.
- `NULL` correction reasons previously bypassed PL/pgSQL `IF` validation through direct RPC calls. New payment-correction/invoice-void wrappers require a non-empty reason and revoke application access to the original internal functions. Existing audit records remain intact.
- Responses now enforce `nosniff`, frame denial, same-origin referrer policy, restricted device permissions, baseline CSP, and production HSTS. `X-Powered-By` is disabled. CSP permits inline framework scripts/styles required by the current App Router setup; it is **not** represented as a nonce-based strict CSP. Production has no `unsafe-eval`. React's escaped rendering and server-side input checks remain essential.
- Session cookies explicitly use `SameSite=Lax` and `Secure` in production, consistently across refresh, server actions and the browser client. Production must run behind HTTPS; local development retains HTTP compatibility. Supabase's browser-session behavior remains supported; these are not represented as HttpOnly cookies. Live session refresh and cookie behavior still require a connected HTTPS acceptance test.
- Protected routes explicitly send private/no-store directives for browsers and CDNs, including no-key redirects. No shared cache is enabled for prices, profiles, orders, invoices, payments or delivery/customer data. Next's image optimizer allows no remote hosts, no SVG, no local-IP fetching and no redirects. Authenticated photos bypass it entirely.

## Performance changes

- Catalogue filters and SKU matching execute in an RLS-aware database RPC, with 24 products per page instead of transferring up to 500. Sorting is stable, oversized page numbers are clamped, and unapproved/anonymous callers are denied. Product details query one UUID directly rather than loading the whole catalogue.
- The order builder receives only product names, IDs, active flags and the required variant fields; it no longer serializes descriptions, warranties, attributes or image manifests. Request-scoped React caches deduplicate repeated Supabase clients/order/customer/invoice/delivery queries without sharing customer data between requests.
- Proxy uses verified JWT claims where supported for refresh; the request data layer still calls `getUser()` and checks trusted profile roles/approval. This avoids an extra remote user lookup when asymmetric token verification is available.
- The landing page reads only the anonymous guest-setting boolean with a 2.5-second timeout, a 30-second public fetch cache and fail-closed behavior. It no longer reads a visitor's Auth session just to render marketing content. Guest admission is always rechecked against the current database setting; the public form can lag a setting change by up to the cache interval.
- The logo is statically imported, producing content-hashed public assets suitable for immutable caching. Framework response compression stays enabled. Private records stay uncached even when that costs an extra request.

No universal speed percentage or production CDN hit rate is claimed. A flat-color orientation/metadata test fixture compressed from 19,212 bytes to 2,984 bytes for its largest WebP; real photographs differ. Measure the deployed site's image transfer sizes, TTFB, LCP and Storage CDN hit/miss headers using representative photos and separate accounts.
